# 계약서 OCR·개인정보 마스킹

## 책임 경계

- `backend/`: 인증, 업로드 검증, OCR worker 호출, 안전 텍스트의 LLM 분석
- `ocr-worker/`: 로컬 PaddleOCR-VL 추론, 개인정보 탐지, 영구 마스킹, 재검증,
  LLM 전달용 텍스트 생성
- `data/`: 공공 법률/RAG 데이터 전용. 사용자 계약서를 저장하지 않음

## 모델

- Hugging Face: `PaddlePaddle/PaddleOCR-VL-1.6`
- 실행: 공식 `PaddleOCRVL`, `pipeline_version="v1.6"`
- 문서 파싱: 전체 layout + VLM 파이프라인
- 마스킹 좌표: 페이지별 `prompt_label="spotting"`
- 도장: `use_seal_recognition=True`

## 처리 흐름

1. 인증된 사용자가 `POST /api/v1/documents/analyze`에 계약서를 업로드한다.
2. 백엔드는 파일 형식과 크기를 확인하고 내부 OCR worker로 전달한다.
3. Worker는 PaddleOCR-VL로 페이지별 텍스트와 좌표를 얻는다.
4. 주민등록번호·전화번호·이메일·계좌번호 및 문맥이 있는 이름을 탐지한다.
5. 같은 탐지 결과로 평탄화 마스킹 PDF와 플레이스홀더 치환 텍스트를 만든다.
6. 치환 텍스트를 다시 검사해 지원하는 개인정보 패턴이 남으면 422로 중단한다.
7. 백엔드는 치환 텍스트만 LLM에 보내 계약 조건과 위험 요소를 구조화한다.
8. 응답에는 분석 결과, 치환 텍스트, 마스킹 PDF(base64), 검토 필요 여부가 담긴다.

원본 OCR 텍스트와 원본 파일은 LLM에 전달하지 않으며 애플리케이션 로그에도
기록하지 않는다. 주소는 세 종류의 부동산 서류가 같은 목적물을 가리키는지 비교하기
위해 마스킹 대상에서 제외하며, 개인정보가 치환된 나머지 OCR 텍스트와 함께 LLM에
전달한다. 현재는 저장소 연결 전 PoC이므로 PDF를 base64로 응답한다. 운영
단계에서는 private Storage의 짧은 만료 다운로드 URL과 비동기 작업 API로 교체한다.

## 남은 작업

1. 실제 한국어 계약서로 v1.6 Spotting 글자·단어 좌표 포맷을 확정한다.
2. 문맥 없는 이름을 처리할 개인정보 NER/정책과 주소 처리 정책을 확정한다.
3. Supabase private Storage와 비동기 작업 상태를 연결한다.
4. 마스킹 전후 개인정보 재현율과 처리시간을 측정한다.
5. 계약서 분석에 필요한 법률 근거를 연결하려면 별도의 RAG 검색 단계를 추가한다.

## 완료 기준

- 주민등록번호·전화번호·계좌번호 테스트셋 재현율을 별도로 보고한다.
- 마스킹 PDF에서 원본 텍스트 레이어와 메타데이터가 남지 않는다.
- 처리 완료 후 임시 원본과 페이지 이미지를 삭제한다.
- OCR 원문과 개인정보를 애플리케이션 로그에 기록하지 않는다.
- 좌표/출력 파싱이 불확실하면 자동 완료하지 않고 `REVIEW_REQUIRED`로 보낸다.
